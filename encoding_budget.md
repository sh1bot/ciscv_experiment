# Encoding budget — does the VLC pairing encoding fit in 32 bits?

Corpus-grounded answer to the question running through `encoding.md`: given the
`g`/`h` variable-length opcode scheme, is there enough bit budget to encode all
the pairing frames, or does the opcode namespace overflow?

**Short answer: it fits, comfortably — at 99% coverage of real corpus pairs, and
with format discrimination costing zero extra bits.** The earlier worry (that
`chain-alu` alone needs 16×16 = 256 codepoints) was a worst-case that never
materialises: the real op-pair distribution is heavily concentrated.

Generated by [`analysis/encoding_budget.py`](analysis/encoding_budget.py) over
`tests/godot.s` + `tests/testcase0.s`. Re-run:

```
python3 -m analysis.encoding_budget tests/godot.s tests/testcase0.s
```

## The model

The 32-bit word (per `encoding.md`): marker `[1:0]=10`, then the fixed-position
opcode namespace **`opcode5[6:2]` + `funct3[14:12]` = 8 bits = 256 leaves**,
with `g`/`h` reserved for the immediate-width VLC, and the rest operands.

Format discrimination is **not** a separate field — it's a prefix code. Each
`(frame, opA, opB)` combination the encoding supports occupies one leaf of the
256-entry `opcode5+funct3` table; decoding that leaf tells you the frame (hence
how to interpret every other field) *and* the two operations at once. So the
only question is: **how many distinct `(frame, opA, opB)` leaves does real code
demand, summed over all frames?** If that sum ≤ 256, everything fits and format
ID is free.

"Leaves for X% coverage" (`L90/L95/L99`) = the number of distinct `(opA, opB)`
pairs, ranked by frequency, needed to cover X% of that frame's real pairings.
`addi` is split into its subforms (`li`/`mv`/`addi4spn`/`addi_rsd`/`addi_other`)
so immediate semantics stay clean. Attribution is greedy first-accepting-rule,
matching how the encoder would pick one frame per pair.

So the entire pairing encoding — all frames, both operations each, format
discrimination included — lives inside the `opcode5+funct3` namespace at up to
99% real coverage, with ~20 leaves still spare. `g` and `h` never have to serve
as opcode bits; they are entirely free for the immediate VLC.

The two biggest tenants are `rsd-alu` (22 @ 95%) and `chain-alu` (47 @ 95%) —
between them ~44% of the budget — exactly the two-independent-ALU frames the
worst-case analysis feared, now shown to need ~70 leaves, not 512.

(The count is conservative: for tuple frames like `dual-arith2` where `opB` is
determined by `opA`, distinct `(opA,opB)` over-counts real leaves, so true
demand is a touch lower.)

## Result 2 — immediate fields: 8 frames need a wide variant

The opcode side fits; the *immediate* side is where the real shortfalls are. A
5-bit field extended by `g,h` reaches 7 bits. Frames whose p95 immediate demand
exceeds that:

| frame | immA@95 | immB@95 | accommodated? |
|---|--:|--:|---|
| load-sp-branch | 8 | — | ✅ sp-relative 10-bit variant |
| store-chain-alu | 7 | 8 | ✅ sp-relative 10-bit variant |
| base-chain-load | — | 8 | ✅ 10-bit `imm[9:5\|4:0]` |
| prologue / epilogue | 9 | 6 | ✅ frame-size `imm×16`, 10-bit |
| **dual-indep-pair** | **10** | 7 | ❌ `li` constant in a 5-bit field |
| **mvload-jump-pair** | **8** | — | ❌ `li` / wide load offset in 5-bit field |

Most "wide" cases are already covered by a dedicated sp-relative or `×16`
10-bit variant in `encoding.md`. The genuine gap is **`li` constants**
(`dual-indep`, `mvload-jump`): they want 8–10 significant bits but sit in a
5-bit `imma`. This is the same un-range-checked `li` immediate flagged earlier
in the rules (`is_li` accepts any concrete value). Options: a dedicated wide-`li`
frame, `lui`-style upper-immediate pairing, or accept the coverage loss.

## Result 3 — the current op-set size is well-matched to the budget

Cross-check with the biclique tiler (`util/biclique_tiling.py`) on the
*generalised* chain opportunity — the full 45-op semantic ALU-chain set with
free registers/immediates, not just the current 16-mnemonic rule — over
godot: **8 opcode bits cover only ~60% held-out** (best split `b=1,w=2,h=5`).
So generalising the ALU chain to every pairable op would blow past the budget
or crater coverage. The current rules' restraint (16 mnemonics per slot) is
close to the most an 8-bit opcode field can carry at high coverage — the frames
are sized about right, not arbitrarily.

(The committed `tiling_N8_best.json` reports 91.6% held-out; that is on the
smaller committed `results/` table. Tiling coverage is corpus- and
vocabulary-dependent — the 60% figure is godot-only over the full 45-op set.)

## Caveats

- **Current-rule demand**, not a generalised encoding. Broadening any frame's
  op set raises its leaf count (Result 3).
- Corpus = godot + testcase0. Two programs; a third would move the tail
  (L99) more than the head (L90).
- Greedy first-rule attribution assigns each real pair to one frame, matching
  the encoder; a different rule order shifts pairs between `rsd-alu` and
  `chain-alu` but not the total.
- A flat 256-entry decode table is assumed; a hierarchical `opcode5 → funct3`
  decode may waste some leaves, but there are ~100 spare at 95% to absorb it.

## Takeaway

The VLC framing was the right call and it closes the budget: **format
discrimination is free, `g,h` are free for immediates, and all 21 frames fit
the 256-leaf opcode namespace at 99% coverage.** The remaining work is on the
immediate side — a wide-`li` story — not the opcode side.
